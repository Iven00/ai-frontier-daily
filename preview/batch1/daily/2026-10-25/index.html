    今日趨勢

    1

    長期記憶回歸「保留原始證據」

    Raw-RAG 論文顯示：只對原始對話做向量檢索加重排序，就在七組設定中的六組勝過十多種代理式記憶系統；同週 Google ADK 2.13 也推出不需要 embedding、以關鍵字回憶的 MongoDB 記憶服務。先把原始資料留好、檢索做紮實，再談萃取與圖譜。

    2

    MCP 從「呼叫工具」走向「代理作業介面」

    Claude Code 開始支援 MCP Tasks（長任務先回 task id、背景執行）與 Elicitations（工具中途向使用者提問）；官方 TypeScript SDK 2.4.0 則加入 Skills over MCP，讓伺服器發布並校驗技能資料夾。MCP 正在補上長流程、人機確認與能力分發三塊。

    3

    語音代理走向全雙工與端側

    Block 發表只用人類語音訓練、可在 MacBook M4 Max 本地執行的全雙工模型 Dessa；sherpa-onnx 2.0.0 持續強化離線 ASR／TTS 跨平台部署；ADK 2.13 的 Live 音訊加入插話（barge-in）。語音不再只是「ASR→LLM→TTS」三段式。

    4

    AI 的價值開始被要求「可證明」

    技術面，Anthropic 與 Theorem 用 Claude 在 123 個開源函式庫的二進位層級產生可機器檢查的證明；商業面，Apollo 首席經濟學家指出科技業以外的企業還看不到 AI 帶來的營收與利潤率改善。不論是程式正確性還是 ROI，都進入要拿證據說話的階段。

    Raw-RAG：只對原始對話做檢索＋重排序，竟勝過多數代理式記憶系統

    arXiv・原始發布 2026-10-22

    把原始對話切成 256 token 視窗、向量取 128 筆再用 cross-encoder 選 15 筆，這個「樸素 RAG」在 4 個記憶基準 7 組設定中 6 組排第一。

    已確認事實
    • Raw-RAG 不做 LLM 萃取、摘要、建圖或改寫：對話帶時間戳記切成 256 token、重疊 32 token 的視窗，向量檢索 128 筆，cross-encoder 重排後取前 15 筆交給閱讀模型。
    • 在 LoCoMo、LongMemEval、MEME、MemoryAgentBench 四個基準、七組「基準×模型」設定中，有六組在受比較的記憶系統裡排第一，領先最強代理式記憶系統 0.13～5.53 分。
    • 對 Mem0 的稽核：UPDATE 與 DELETE 只占 LoCoMo 寫入決策的 4.39%、LongMemEval 的 2.46%；把更新改成只新增，LoCoMo 準確率由 67.36% 升到 69.42%。
    • 消融：拿掉重排序器總分降 3.92 分；加上原子事實萃取降 19.62 分、加摘要降 5.81 分、加圖譜擴展降 5.78 分。
    • 效率：在 MEME 10 段對話、110 題上，Raw-RAG 建索引＋檢索共 305.91 秒，比次快系統快 5.1 倍、比 EverMemOS 快 30.4 倍。
    • 作者自承限制：只測離線、公開基準上的對話，不代表互動式、多模態或實際營運場景；保存原始歷史也帶來儲存與隱私問題。
    解析
    • 核心方法：把「證據覆蓋率」與「閱讀模型利用率」拆開量測，證明系統間差距主要來自能不能把足夠證據（含依賴路徑）送到閱讀模型前，而不是讀完後會不會答。
    • 差異：多數記憶系統在寫入時就萃取、合併、改寫，等於提早丟資訊；Raw-RAG 把狀態推理留給閱讀時的強模型。論文也指出過去評測中 RAG 基線常用過粗的切塊、過淺的檢索或沒有重排序。
    • 結果與限制：結果依賴強閱讀模型（GPT-4.1-mini、DeepSeek-V4-Flash 等）；在 PersonaMem-v2 只排第三；MEME 的 cascade、deletion 類題目分數仍很低。皆為作者自述，未獨立重現。
    • 與你的關聯：對你規劃的個人代理／會議助理記憶層是直接的設計指引：先做「原始證據可回溯」的檢索基線（含重排序），任何知識圖譜或摘要層都必須證明能勝過它。
    尚待驗證（推測）
    • 記憶系統評測可能會把「調校良好的 Raw-RAG」列為必比基線，部分記憶新創的差異化敘事會受挑戰。
    • 圖譜與摘要的價值可能轉向「省 token、可解釋、權限與刪除管理」，而不是準確率。
    建議下一步　用你自己的會議或對話紀錄，照論文參數（256/32、top-128→rerank top-15）做一個 Raw-RAG 基線，再拿目前的記憶或圖譜方案對比。

    Anthropic × Theorem：Claude 在 123 個開源函式庫的機器碼層級產生可檢查的形式化證明

    Anthropic・原始發布 2026-10-22

    把 OSS-Fuzz 的模糊測試入口改寫成規格，讓 Claude 證明「64MB 以內任何輸入都不會當機」，共 239 個入口、約 1.8 億行 Rocq 證明。

    已確認事實
    • Claude 為 123 個 OSS-Fuzz 函式庫的 239 個模糊測試入口，證明在 RISC-V 編譯後的二進位上，任何小於 64MB 的輸入都不會觸發記憶體安全錯誤或斷言失敗。
    • 證明約 1.8 億行 Rocq，典型一份約 60 萬行，對應中位數約 18,000 條 RISC-V 指令；由 Rocq 證明檢查器機械驗證。
    • 前提假設：單執行緒、靜態連結 musl、固定記憶體預算、Linux 行為以模型描述；尚未涵蓋 x86／ARM 與動態連結 glibc。
    • 過程中找到並修補模糊測試難以發現的錯誤，例如需約 20MB 特殊輸入才觸發的越界寫入，並重新發現 libexpat 的 CVE-2026-56132。
    • Opus 5.5 在 36 個小型驗證任務上，證完一半所需 token 比 Opus 5 少約 40%；共享證明工作區讓代理少用 17% token。
    • 公開子集證明與 RISC-V／OS 語意；Theorem 提供替其他開源專案跑同一流程，並發布 Claude skill。
    解析
    • 核心方法：不要求人寫規格，而是把既有測試（fuzz entry point）自動轉成「永不當機」規格，再讓代理在機器碼層級寫證明、由證明檢查器把關。
    • 差異：傳統形式化驗證（如 seL4）要數十人年；這裡把規格來源換成現有測試、把證明工作交給代理，並靠證明重用攤提成本。
    • 結果與限制：只證明模型化環境下的特定性質，不等於無錯誤；ASan 也抓不到所有記憶體問題；證明要上億 token，成本仍高。數據為 Anthropic 自述。
    • 與你的關聯：對做 AI 產品的你，重點是「代理輸出可被機器驗證」的工作模式：讓代理做大量苦工，但最終由確定性檢查器裁決，這也適用於資料管線、規則引擎等場景。
    尚待驗證（推測）
    • 關鍵開源依賴（如 OpenSSL、curl）可能出現「已證明」標章，成為供應鏈安全的新指標。
    • 「代理＋確定性驗證器」可能成為高風險領域導入代理的標準架構。
    建議下一步　讀原文的 Limitations 與證明重用章節，思考你的產品中哪些環節可以用確定性檢查器（測試、schema、規則）裁決代理輸出。

    Block 發表 Dessa：只用人類語音訓練、可本地執行的全雙工語音模型

    Block・原始發布 2026-10-23

    Dessa 沒有文字、沒有預訓練模型，從零只聽人類對話學會即時聊天，能同時聽與說，並在 MacBook Pro M4 Max 上本地跑。

    已確認事實
    • Dessa 是語音進、語音出的全雙工模型，能邊聽邊說，會插話與附和（例如「嗯」「對」）。
    • 官方稱從零只用人類對話語音訓練，不用文字與預訓練模型；訓練只用一套 NVIDIA GB200 NVL72。
    • 推論快於即時，可在 MacBook Pro M4 Max 或更高等級電腦本地執行。
    • 目前沒有公開權重或 API；先開放少數 AI 安全研究者早期測試。
    • 官方稱所學單字量比 LLM 少數百倍，但未公布正式評測數據。
    解析
    • 核心方法：直接以音訊為建模單位，讓情緒、語氣、停頓、插話時機都留在同一個模型裡，而不是經過文字轉換。
    • 差異：主流做法是 ASR→LLM→TTS 串接或以文字驅動語音；Dessa 主張文字會丟掉語氣資訊，因此完全不經文字。
    • 結果與限制：只有官方示範錄音、沒有基準測試；知識完全來自語音資料，事實正確性與工具使用能力未知；尚無法取得。
    • 與你的關聯：你關注 ASR／TTS 與會議助理：Dessa 代表「端側、能聽懂情緒」的方向；但短期內實務仍是串接架構，可把它當研究標竿與產品體驗參考。
    尚待驗證（推測）
    • 全雙工純語音模型可能先在陪伴、客服、點餐等「閒聊比知識重要」的場景落地。
    • 語音模型能聽出情緒，也會帶來語音詐騙與操縱等新的安全議題，這正是官方先找安全研究者的原因。
    建議下一步　聽官網的示範錄音，記下插話、附和、情緒轉折的時間點，作為你未來語音代理體驗設計的對照標準。

    Claude Code 支援 MCP Tasks 與 Elicitations：工具可背景長跑、也能中途問你

    Claude Code Docs・原始發布 2026-10-23

    慢工具先回一個 task id，Claude Code 繼續做事並輪詢結果；工具也能跳出表單問使用者「要部署到 staging 嗎？」。

    已確認事實
    • MCP Tasks 為公開測試版，需 Claude Code v2.1.304 以上，適用終端機互動、Agent SDK 與 GitHub Actions；VS Code 擴充與桌面版尚未支援。
    • Tasks 來自 MCP 2026-07-28 版的 Tasks 擴充：伺服器先回 task 控制代碼，客戶端以 tasks/get 輪詢，可取消。
    • Elicitation 讓 MCP 伺服器在任務中途向使用者發問，Claude Code 以小表單呈現；非互動模式會請伺服器取消需要輸入的任務。
    • 主對話中執行超過兩分鐘的 MCP 呼叫會被自動移到背景。
    • 官方表示 Tasks 與 Elicitations 會擴展到更多 Claude 產品。
    解析
    • 核心方法：把工具呼叫從「同步請求」改成「非同步任務＋中途人機確認」，讓代理能委派深度研究、部署這類長流程。
    • 差異：過去 MCP 工具若跑很久只能阻塞或逾時，需要確認時只能結束再重來；現在協定層就有任務生命週期與提問機制。
    • 結果與限制：仍是 beta，子代理、一次性 claude -p 執行不適用；Upstash 文章是第三方實作經驗。
    • 與你的關聯：你設計的個人任務管理、會議後續追蹤代理，正需要「背景長任務＋關鍵步驟請使用者確認」，可直接依這個協定設計 MCP 伺服器。
    尚待驗證（推測）
    • Elicitation 可能成為代理執行高風險動作（付款、寄信、刪除）前的標準確認介面。
    • 長任務協定成熟後，「代理排程器」可能變成 MCP 生態的新產品類別。
    建議下一步　寫一個最小 MCP 伺服器：一個會跑 30 秒的報告工具（回 task id）＋一個執行前用 elicitation 要求確認的工具，在 Claude Code 測試。

    MCP 官方 TypeScript SDK 2.4.0：加入 Skills over MCP（SEP-2640）

    GitHub・原始發布 2026-10-23

    伺服器可用 loadSkills(folder) 發布一整個技能資料夾，客戶端 SkillsClient 會校驗大小、雜湊與 SKILL.md frontmatter。

    已確認事實
    • 新增 Skills 擴充（SEP-2640）：伺服器提供 skills/list、skills/get 與 skill:// 資源，客戶端可列出、讀取並驗證技能。
    • 讀取時會驗證檔案大小、摘要（digest）與 SKILL.md frontmatter，不符時拋出 SkillVerificationError。
    • 同時支援 2025-11-25 與 2026-07-28 協定版本；attach 介面標為 experimental。
    • 升級注意：依 2026-07-28 規格，number 型別參數上的 x-mcp-header 會被拒絕。
    • 新增 OAuth refresh 可選擇帶 scope，以相容 Microsoft Entra ID。
    解析
    • 核心方法：把「技能」（說明文件＋腳本）變成可透過 MCP 發布、快取與驗證的資源，而不是各家代理各自的本地資料夾。
    • 差異：過去技能多半隨代理產品綁定；現在可由伺服器集中發布，任何支援 MCP 的客戶端都能取得並校驗完整性。
    • 結果與限制：attach 仍為實驗性，可能在小版本變動；生態系客戶端支援程度未知。
    • 與你的關聯：你若要做企業知識庫或垂直代理，可以把領域 know-how 打包成 skills 經 MCP 發布，搭配上一則的 Tasks 形成完整能力分發。
    尚待驗證（推測）
    • 企業內部可能出現「技能登錄中心」，以 MCP 統一發布與版本管理代理技能。
    • 技能的簽章與供應鏈安全可能成為下一個議題。
    建議下一步　把你現有的一份工作流程說明寫成 SKILL.md，用 SDK 2.4.0 的 loadSkills 發布並用 SkillsClient 讀回驗證。

    Google ADK Python 2.13.0：分類器路由、Live 音訊插話、免 embedding 的 MongoDB 記憶

    GitHub・原始發布 2026-10-23

    12 個實驗功能轉穩定，新增 ClassifierNode 路由、Live 語音插話、MongoDB 對話與長期記憶；遙測預設改為 OpenTelemetry GenAI v2（破壞性）。

    已確認事實
    • 新增 BaseClassifier、ClassifierNode 與 TypesafeClassifier，可用 TypeSafe 的 Jev 模型在工作流中做路由；官方稱單次前向計算回傳校準機率，比 LLM 快很多。
    • Live 音訊支援 barge-in（插話），並整合 Gemini 語音轉文字與文字轉語音。
    • MongoDbSessionService 可跨副本共享對話；MongoDbMemoryService 以關鍵字比對回憶過往對話，不需要向量索引（皆為實驗性）。
    • BaseMemoryService 新增 delete_memory API。
    • 字串模型代理單回合由 20ms 降至 2.5ms；遙測預設改為 OpenTelemetry GenAI semconv 1.44，移除 call_llm span。
    解析
    • 核心方法：在框架層把「便宜的分類決策」「即時語音」「可刪除的長期記憶」做成標準元件。
    • 差異：與前一期 OpenAI Decisions API 同一方向：路由交給專用小模型；記憶方面則提供不依賴 embedding 的最簡方案。
    • 結果與限制：效能數字為官方自述；MongoDB 記憶為實驗功能，關鍵字回憶的召回品質未知；遙測變更需調整既有監控。
    • 與你的關聯：做多代理或語音代理原型時可直接利用；delete_memory 對個人資料刪除權（隱私合規）也很實用。
    尚待驗證（推測）
    • 「分類器節點」可能成為各代理框架的標配，LLM 只在必要時被呼叫。
    建議下一步　若使用 ADK，升級前先檢查 OpenTelemetry 監控；試用 ClassifierNode 把意圖路由從 LLM 移出並量測延遲。

    sherpa-onnx 2.0.0：離線 ASR／TTS 工具鏈升級主版本，擴大跨平台與 HLG 解碼支援

    GitHub・原始發布 2026-10-23

    不需網路的語音辨識、合成、VAD、說話人工具包推出 2.0：離線 CTC 支援 HLG 解碼、Windows ARM64、Python 3.15，並移除 espeak-ng 依賴。

    已確認事實
    • 離線 CTC 模型在 C、C++、JNI／Kotlin／Java、WASM API 支援 HLG 解碼。
    • 串流 NeMo transducer 支援帶熱詞（hotwords）的 modified_beam_search。
    • 新增 Qwen3 ASR、Doubao ASR 的字幕產生範例，與 Kokoro 多語 TTS 的 WASM 示範。
    • Flutter 與 Node.js 支援 Windows ARM64；提供 Python 3.15 wheels。
    • 移除 espeak-ng 與 piper-phonemize 依賴；修正長串流 VAD 的 SIGSEGV 等多項錯誤。
    解析
