OpenAI Decisions API 正式上線：把分類與路由從大模型生成中拆出

FACT｜已確認事實
  • 端點為 POST /v1/decisions，目前唯一支援模型為 gpt-6-luna。
  • 回傳三種答案型別：probability（機率）、choice（固定選項）、score（依評分準則）。
  • GA 新增：GPT-Live 原生整合、提示快取、美國／歐盟推論駐留、原生 JSON 輸入、題目說明可含圖片；每次請求上限由 200 題增為 400 題。
  • 官方引用客戶說法：Speak 的下一步動作時間由 1.4 秒降到 0.13 秒；Sierra 稱 p95 低於 280 ms。
  • TechCrunch 將其定位為與新創 TypeSafe 的 Jev「決策模型」競爭。
ANALYSIS｜解析
  • 核心方法：把代理流程中大量「有限答案」的小決策（路由、分類、風險分級）交給專門的決策介面，而非讓 LLM 生成文字再解析。
  • 差異：相較傳統用 LLM＋結構化輸出做分類，省去生成步驟，延遲與成本大幅下降，並直接給出信心值。
  • 結果與限制：加速倍數與客戶數字皆為廠商與客戶自述；只綁定單一模型，供應商鎖定風險高。
  • 與你的關聯：你的會議助理與任務管理產品中，意圖判斷、優先序、是否需要人類確認等，都很適合這種「System 1」層；也可用開源小模型自建同等介面。
HYPOTHESIS｜尚待驗證
  • 「決策模型」可能成為代理架構的獨立一層，與規劃用大模型分工，類似快思／慢想。
  • 各家可能跟進推出同類 API，或在開源界出現專門的決策 SLM。
建議下一步
  • 從你的代理流程挑 3 個高頻分類點，比較「LLM＋JSON 輸出」與「決策型介面（或本地小模型）」的延遲與準確率。

Podcast 逐字稿（這一則）

曉晨：第三則，七十九分，OpenAI 的 Decisions API 正式上線。

曉晨：我先問一個笨問題，為什麼分類這種事，不直接叫大模型輸出 JSON 就好？

雲哲：不笨，這正是重點。Decisions API 就是把分類跟路由從大模型的生成裡拆出來。端點是 POST v1 decisions，目前只支援一個模型，gpt-6-luna。

雲哲：它回傳三種答案：機率、固定選項，或依評分準則給的分數。這次正式版加了 GPT-Live 原生整合、提示快取、美國跟歐盟的推論駐留，每次請求的題數上限也從兩百題加到四百題。

曉晨：那速度到底快多少？

雲哲：官方引用客戶說法：Speak 的下一步動作時間，從一點四秒降到零點一三秒；Sierra 說 p95 延遲低於兩百八十毫秒。

曉晨：快了十倍？

雲哲：先別急著相信。這些都是廠商跟客戶自述，而且只綁一個模型，供應商鎖定的風險很高。

曉晨：所以比較像是一種架構概念，不一定要用他們家的。

雲哲：對！你的會議助理裡，意圖判斷、優先序、要不要人類確認，都很適合這種「快思」層，也可以用開源小模型自己做同樣的介面。下一步就是挑三個高頻分類點，實際比一比延遲跟準確率。
